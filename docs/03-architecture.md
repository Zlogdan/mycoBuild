# Этап 2. Архитектура

Принцип: **данные из игры важнее ТЗ**. Где правило взято из кода игры, указан метод-источник.

## 1. Технологический стек

| Слой | Выбор | Почему |
|---|---|---|
| Сборка | **Vite** | быстрый dev-сервер, статическая сборка (GitHub Pages / любой хостинг), без бэкенда |
| Язык | **TypeScript (strict)** | геометрия и солвер — код, где ошибки типов дорого стоят |
| UI | **React 18** | компонентная модель для панелей, каталога, вариантов раскладки |
| Состояние | **Zustand** | один небольшой стор билда, без бойлерплейта Redux; легко сериализуется в JSON |
| Отрисовка сетки | **SVG** | ≤ 8×7 ячеек: SVG даёт чёткие гексы при любом масштабе, нативный hit-test, CSS-подсветку |
| Drag & Drop | **Pointer Events** (свои) | HTML5 DnD не позволяет вращать фигуру во время перетаскивания (колесо/R) и плохо работает на тач-экранах, а мобильную версию ТЗ закладывает на будущее |
| Автоподбор | **Web Worker** | поиск не блокирует интерфейс, есть прогресс и отмена |
| Тесты | **Vitest** | тот же конфиг, что у Vite; ядро тестируется без браузера |
| i18n | свой словарь `ru.json` / `en.json` | игровые тексты уже в RU/EN в `game.json`, библиотека не нужна |

## 2. Структура проекта

```
mycoBuild/
  extractor/            Python: извлечение данных из игры → site/data
  site/                 веб-приложение (Vite root)
    public/data/
      game.json               ← генерируется, не редактировать
      stats.overrides.json    ← ручные подписи характеристик (экстрактор только дополняет)
      patches.json            ← ручные правки/добавления модов, оружия, персонажей
      icons/
    src/
      core/             ЧИСТЫЙ TypeScript, без React и DOM → тестируется в Node
        hex.ts          координаты, повороты, нормализация паттернов
        pattern.ts      Pattern: ячейки, 6 ориентаций, валидация
        board.ts        доска W×H, расширители, битовые маски
        rules.ts        правила игры: вращение по уровню, дубли, роли модов
        placement.ts    проверка размещения, перечисление допустимых позиций
        solver/         автоподбор (branch & bound), запускается в воркере
        build.ts        модель билда + JSON schemaVersion 1 (экспорт/импорт/миграции)
      data/             загрузка game.json, применение patches/overrides, валидация базы
      ui/               React-компоненты
      i18n/
      worker/solver.worker.ts
    tests/              Vitest
  docs/
```

Зависимости строго в одну сторону: `ui → core, data`; `data → core`; `core` ни от чего не зависит.

## 3. Модель данных

### 3.1 Слои данных
1. `game.json` — генерируется экстрактором (источник истины, перезаписывается при каждом обновлении игры).
2. `patches.json` — ручные изменения поверх, слияние по `id`:
   ```json
   { "upgrades": { "40688": { "pattern": {...} }, "custom-1": { ...новый мод... } },
     "gears": { "...": { "upgrades": { "add": ["custom-1"], "remove": [] } } } }
   ```
3. `stats.overrides.json` — подписи характеристик (en/ru/format) по ключу `<PropertyType>.<field>`.

При загрузке модуль `data/validate.ts` проверяет базу: ссылки gear→upgrade существуют, паттерн не пустой, ячейки
лежат внутри `w×h`, паттерн связный (иначе — **предупреждение**: в игре есть 3 несвязных мода), id уникальны.

### 3.2 Сущности (TypeScript)
```ts
type Rarity = 0|1|2|3|4|5;          // Standard, Rare, Epic, Exotic, Oddity, Contraband
type Cell = { q: number; r: number }; // axial
interface Upgrade {
  id: string; key: string; name: Loc; desc?: Loc; icon: string;
  rarity: Rarity; effect: string; flags: string[];
  role: 'normal' | 'gridExpander' | 'ability';
  pattern: { w: number; h: number; cells: [x, y, connections][] };
  props: { type: string; data: Record<string, unknown> }[];
  gears: string[];
}
interface Gear { id: string; key: string; name: Loc; category: 'character'|'primary'|'heavy'|'throwable'|'special'|'global';
  grid: string; ability?: string; upgrades: string[]; icon: string }
```
Пул модов персонажа = его `upgrades` + пул `global` (`player`, 41 мод), как в `GearData.CanEquipUpgrade`.

## 4. Математическая модель гекс-сетки

### 4.1 Координаты
- **Доска** хранится как в игре: offset **odd-q**, `x` — столбец (0…W-1), `y` — строка (0…H-1), гексы с плоским верхом,
  нечётные столбцы сдвинуты вниз на ½ ячейки (`HexMap.HexToCube`).
- **Паттерны и вычисления** — в **axial** `(q, r)`: `q = x`, `r = y − (x − (x&1)) / 2`.

Почему так: в axial поворот — перестановка координат, а сдвиг фигуры — сложение векторов, одинаковое для чётных и
нечётных столбцов. В offset сдвиг на нечётное число столбцов меняет форму, отсюда костыль `AdjustRow` в коде игры.
Offset остаётся только на границе доски (отрисовка, проверка `0 ≤ x < W, 0 ≤ y < H`, экспорт).

### 4.2 Вращение (как в `HexMap.RotateCube`)
Шаг 60°: кубические `(x, y, z) → (−y, −z, −x)`; биты `connections` циклически сдвигаются на 1 (6 бит: N, NE, SE, S, SW, NW).
После поворота паттерн нормализуется (min q, min r → 0). Для каждого мода заранее считаются **уникальные** ориентации:
симметричные фигуры дают меньше 6 вариантов, что сокращает перебор. Зеркала нет (как в игре).

### 4.3 Размещение
Мод с ориентацией `k` и якорем `(q0, r0)` занимает ячейки `cell + (q0, r0)`. Размещение допустимо, если все ячейки
лежат на доске и не заняты (`GearData.CanEquipUpgrade` + занятость клеток). Для доски до 8×7 = 56 ячеек занятость —
**битовая маска** (`bigint` в UI, пара `uint32` в солвере), пересечение — `(mask & occupied) == 0`.

### 4.4 Размер сетки и расширители
- `size = GridProfile[gear.grid]` по **уровню оружия/персонажа**: ищется последняя запись с `level ≤ уровень`
  (`GridProfile.GetUpgradeGridSize`).
- Расширители (`role: gridExpander`: GridGrow «Нарушение границ», GridGrowC «Нечёткий край», 1 клетка):
  каждый даёт **+1 столбец справа** или **+1 строку снизу**. В игре направление определяется сидом экземпляра,
  поэтому на сайте его **выбирает пользователь** (переключатель на размещённом моде).
- Оба мода не `CanStack`, значит каждый можно поставить один раз. Итого максимум 2 расширителя на сетке
  (по одному каждого вида). `ModifyGridSize` в игре суммирует все.
- Зацикливание (расширитель стоит в клетке, которую сам и добавил) запрещается: расширитель должен лежать внутри
  доски, посчитанной без него.
- Если после снятия расширителя моды оказываются вне доски, они помечаются как недопустимые (красным), а не удаляются молча.

## 5. Правила (`core/rules.ts`)

| Правило | Значение | Источник |
|---|---|---|
| Вращение | по редкости и **уровню аккаунта**: Standard ≥ 3, Rare ≥ 8, Epic ≥ 16, Exotic/Oddity/Contraband ≥ 30 | `PlayerData.UpdateRarityRotations`, `CanRotateUpgrade` |
| Без вращения | мод ставится только в исходной ориентации (0) | там же |
| Дубли | только с флагом `CanStack` (56 модов); остальные — 1 экземпляр | `UpgradeFlags.CanStack`, UI «Stackable», подтверждено пользователем |
| Режим Уроборос | моды `OnlyInOuroboros` исключены экстрактором | решение пользователя |
| Способности | `role: ability` не показываются в каталоге | `Character.DefaultUpgrade` |
| Пространственные моды | флаг `IsSpatial` (16 шт.): на доске подсвечиваются соседние клетки и показывается подсказка об эффекте; на допустимость и счёт не влияют | решение пользователя |

## 6. Алгоритм автоподбора (`core/solver`)

Задача: взвешенная упаковка гекс-полимино в прямоугольник, максимизировать сумму весов. На входе: выбранные моды
с весами (у `CanStack` — желаемое количество копий), доска, разрешённые ориентации, зафиксированные пользователем
моды (можно «закрепить» часть раскладки) и опции расширителей.

**Точный перебор с отсечениями (branch & bound)** — реализовано в `site/src/core/solver/solve.ts`:
1. Предрасчёт: каждое размещение (ориентация × якорь) каждого мода — битовая маска доски (до 128 клеток).
   Размещения проиндексированы по своей «первой» клетке (в порядке строк).
2. **Ветвление по первой нерешённой клетке**: она либо покрывается размещением, у которого это первая клетка
   (моды пробуются по убыванию веса), либо навсегда остаётся пустой. Каждая раскладка достигается ровно один раз,
   копии одного `CanStack`-мода не дают перестановок.
3. Верхняя граница = текущий вес + дробный рюкзак оставшихся копий по нерешённым клеткам. Пустые клетки сразу
   уменьшают ёмкость, поэтому граница сильная.
4. Расширители — внешний цикл (не использован / столбец / строка). Использованный расширитель обязателен
   и ставится только в пределах сетки без его собственного расширения.
5. Варианты: top-K решений, которые отличаются набором модов или, при том же наборе, хотя бы половиной позиций.
6. Остановка: исчерпан перебор (доказанный оптимум); или размещено всё выбранное (оптимум по определению, ещё
   ≤0.8 с на добор вариантов); или лимит времени / «Стоп» (показывается «лучшее найденное»).
7. Работает в Web Worker (`src/worker`), шлёт прогресс с текущими вариантами; «Стоп» завершает воркер и
   берёт последний снимок.

Замеры (7×6, уровень 30): 10 модов, всё помещается — 0.1 с; 14 модов на 54 клетки (больше сетки) — доказанный
оптимум за 0.2 с; тяжёлое оружие 5×5 с 14 модами — 15 мс. Сложный случай: 14 модов персонажа на 48 клеток —
не доказывается за 4 с (выдаётся лучшее найденное).

Запас производительности: мемоизация по (клетка, маска), запрет «мёртвых» клеток, ILP/SAT через тот же интерфейс.

Результат: варианты (переключение), суммарный вес, размещённые и неразмещённые моды, «применить», после чего
раскладку можно продолжить править вручную.

## 7. Формат билда (JSON, schemaVersion 1)

```json
{
  "schemaVersion": 1,
  "app": "mycobuild",
  "gameData": { "extractedAt": "2026-11-09T19:19:16Z" },
  "gear": { "id": "…", "key": "accelerator" },
  "levels": { "account": 30, "gear": 10 },
  "grid": { "base": { "w": 7, "h": 6 }, "expanders": [ { "upgradeId": "…", "direction": "column" } ] },
  "placed": [
    { "upgradeId": "3147342", "key": "AKillRate", "x": 2, "y": 1, "rotation": 3 }
  ],
  "autofill": { "selection": [ { "upgradeId": "3147342", "weight": 10, "count": 1 } ] }
}
```
- Позиция: `x, y` — offset-координаты (как в игре) ячейки нормализованного повёрнутого паттерна с минимальными
  `(q, r)`; `rotation` — 0…5 шагов по 60°.
- В каждой записи есть и `upgradeId`, и `key`: если после обновления игры `id` поменяется, мод найдётся по `key`.
- Импорт: JSON-схема → проверка версии (миграции `v1 → vN`) → разрешение модов → проверка каждого размещения
  по правилам. Ошибки показываются построчно («мод X не найден», «мод Y выходит за сетку при уровне 2»),
  восстанавливается всё, что валидно.
- Ссылка на билд (Этап 5): тот же JSON → сжатие (deflate) → base64url в `#hash`, сервер не нужен.

## 8. Интерфейс (desktop-first)

```
┌──────────────┬────────────────────────────────────┬──────────────────────┐
│ Выбор:       │  [Уровень аккаунта] [Уровень оружия]│ Каталог модов        │
│ персонажи /  │                                    │ поиск, фильтры        │
│ оружие       │        ГЕКС-СЕТКА (SVG)            │ (редкость, стихия,    │
│ (иконки)     │                                    │  клетки, можно дубли) │
│              │  панель: повернуть / удалить /     ├──────────────────────┤
│              │  очистить / импорт / экспорт       │ Автоподбор: выбранные │
│              │                                    │ моды + веса, варианты │
└──────────────┴────────────────────────────────────┴──────────────────────┘
```
Подсветка: зелёный силуэт — можно поставить, красный — нельзя (с причиной: «за границей», «пересечение»,
«вращение откроется на уровне 16»); занятые и свободные клетки различаются заливкой.
Управление: перетаскивание мышью, R или колесо — поворот, Del/ПКМ — удалить, двойной клик по моду в каталоге —
поставить в первое свободное место.

## 9. Тестирование (Vitest, без UI)

- `hex`: offset↔axial туда и обратно на всех клетках 8×8; 6 поворотов = тождество; поворот совпадает с
  эталонами из игры (повтор логики `RotateCube`/`CircularShiftLeft6Bits`); сдвиг биты связей.
- `pattern`: число уникальных ориентаций у симметричных фигур; валидация (пусто, вне w×h, несвязно).
- `placement`: границы (все 4 стороны, нечётные столбцы), пересечения, расширители (+столбец/+строка, цикл запрещён,
  снятие расширителя), блокировка вращения по редкости и уровню, дубли `CanStack`.
- `solver`: сравнение с полным перебором на малых досках, известные оптимумы, «все помещаются», «ничего не
  помещается», приоритеты (лёгкий тяжёлый мод против нескольких лёгких), детерминированность.
- `build`: экспорт → импорт = исходный билд; битый JSON, неизвестная версия, отсутствующие моды.
- Smoke-тест по реальной базе: каждый паттерн из `game.json` проходит валидацию и 6 поворотов.

## 10. Порядок работ

Этап 3: каркас Vite+React+TS, ядро `core/*` с тестами, выбор оружия/персонажа, уровни, сетка, каталог,
ручное размещение и вращение. Этап 4: солвер в воркере и UI весов и вариантов. Этап 5: экспорт, импорт и ссылка.
Этап 6: проверка паттернов в игре на реальных билдах.
